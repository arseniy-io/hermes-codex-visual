# Сохранённые подписи инструментов MCP

Companion сохраняет данные, которые Hermes получает от MCP, но теряет при переводе инструмента в формат модели: `title`, `annotations.title` и только две строки `_meta`: `openai/toolInvocation/invoking` и `openai/toolInvocation/invoked`. Произвольный `_meta`, аргументы и результат вызова в снимок не попадают. Исходные имя сервера и имя инструмента сохраняются для точного соответствия; сгенерированное имя не разбирается обратно.

## Передача

`tools.mcp_tool.MCPServerTask._tools` или кэш того же owning profile → начало текущего вызова → `labels[].display` → штатный Desktop `labelArgs` → `args.hermes_tool_labels[].display` → `integrationData`.

До сохранения результата тот же снимок записывается в `display_metadata.tool_result_metadata.hcv_tool_display`. В истории он присоединяется к копии аргументов по `_tool_call_uid` результата и `_tool_call_uids` ассистента. Имя, позиция в очереди, время и повторяющийся provider call ID не используются для исторического сопоставления. Запрос страницы REST при необходимости читает только сохранённые sidecar нужных UID из той же базы профиля. История без снимка остаётся без неизвестных подписей; текущий каталог не переписывает прошлое.

История и события получают только копии. Реальные tool args, схема для модели и сохранённые аргументы не меняются. `display_metadata` уже исключается штатным builder запросов Hermes из контекста модели. В нативном Desktop дополнительное поле `display` проходит внутри уже существующего массива labels, скрытого из панели аргументов. Пересборка Desktop не требуется. Сгенерированный контракт Python/TS/OpenRPC дополнен необязательным полем `ToolLabel.display`, а не новым аргументом инструмента.

У старого lazy schema cache подписи могут отсутствовать до первого нового `tools/list`. Если к началу вызова известна только идентичность, необязательные данные дополняются к завершению этого же вызова. Кэш следующих новых вызовов уже содержит разрешённые поля. Изменившийся каталог не заменяет известный снимок выполняющегося вызова.

## Проверка и установка

`manifest.json` содержит SHA-256 конкретного установленного owning source и кандидата. `core.patch` применяется только к точному исходному хешу. Стадирование принимает также уже установленный точный кандидат. Несовместимое ядро, чужой helper и изменённый staged файл отклоняются.

1. `python -B scripts/stage-hermes-tool-display.py` создаёт только `.local/hermes-tool-display-check/candidate`.
2. `python -B verification/tool-display-core.test.py` проверяет literal snapshots, UID/profile/history, неизменность tool args, реальные функции lifecycle и stage/install/rollback в отдельном временном дереве.
3. `python -B scripts/install-hermes-tool-display.py --install` устанавливает ровно staged байты. Установщик сохраняет originals в `.local/tool-display-core-rollback-*`, публикует helper первым, проверяет результат и автоматически откатывает свои записи при сбое. Gateway перезапускается штатно только после завершения активной работы.

При установке из ZIP распаковать пакет и выполнять команды из его корня; `--candidate` позволяет указать уже проверенный staged каталог. Флаг `hermesToolDisplayCore: true` включает companion и оба скрипта в ZIP. Установщик не меняет профиль, сообщения и каталог интеграций.

Нативная связь с полным transcript субагента проверяется дополнительно в реальном child gateway: raw owning REST `/api/sessions/{id}/messages` сохраняет tool_calls/content/UID, в отличие от компактного RPC отображения. Изолированные тесты Python не заменяют этот сценарий.

Эталон подписи: Codex Desktop 26.1111.2228.0, `164460.04c053ee6e.js` module `alO6.CK/tx`; title fallback `907538.0572f09d40.js` module `mnR8.f8`. Подписи интеграции берутся из локали; снимок задаёт только значения данных.
